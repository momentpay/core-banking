## 1. Purpose

A small pure library with no database and no clock. It defines currency and money, the rounding rules, day-count conventions and the interest arithmetic that deposits and loans both use. Every monetary value in the system passes through it, which is how we keep float arithmetic out of a ledger. It is the first module to build because everything else depends on its exactness and it can be tested completely in isolation, including against Fineract's own numbers.

## 2. Responsibilities

- `Money`: a `Decimal` amount with a currency and a scale taken from the currency's decimal places; arithmetic that refuses to mix currencies
- Currency registry matching Fineract's `m_currency` and the per-tenant `m_organisation_currency` selection, including `decimal_places`, `currency_multiplesof` and display symbol
- Rounding policy as an explicit input to every operation that rounds, never a global default hidden in a process (Fineract keeps a global rounding mode in `MoneyHelper`; ours is passed in)
- Day-count conventions used by interest calculation (days in year and days in month strategies)
- Interest primitives shared by savings and loans: simple and compound factors, period fractions, effective rates
- Property-based tests and a golden-master suite comparing results with Fineract on generated inputs

## 3. Out of scope

- Loan schedules and savings postings: they use these primitives but live in ecb_loans and ecb_deposits
- Any database access, configuration lookup or clock: callers pass everything in
- Exchange-rate conversion (not part of the Fineract design we are following)

## 5. API scope

This module exposes no operations. Currency endpoints (`/v1/currencies`) are served by ecb_org.

## 6. Data model

This module owns no tables. The `m_currency` and `m_organisation_currency` tables are owned by ecb_org, which feeds currency definitions into this library.

## 7. Design to follow

- Pure functions on immutable structs. No process state, no `Application.get_env`, no `DateTime.utc_now`
- `Decimal` context is set explicitly per call (precision and rounding), because Fineract's results depend on rounding at specific steps, not only at the end
- Rounding modes are an enumeration with the same names as Fineract's configuration so tenant settings map one-to-one
- Every function documents which Fineract class it mirrors, so a difference can be traced to the original rule
- Golden master: `parity/scripts/gen-money-golden.sh` runs Fineract's real `Money` class (from the 1.16.1 binary release) on 130,144 generated cases and writes a compressed fixture; `golden_test.exs` replays every case and requires an identical result. It covers all 7 rounding modes, 8 currencies (including 'in multiples of'), negatives, ties and 22-digit factors, and cases where the tenant rounding mode differs from the operation's
- The golden master found that Decimal 2.4.1's context rounding differed from Java (its `:up` mode rounded up even when every discarded digit was zero; Decimal 3 fixed it). `ECBMoney.Precision` does significant-digit rounding and division explicitly on exact values so results never depend on a library's context implementation. Do not replace it with `Decimal.Context` without re-running the golden master
- Zero has no sign: `BigDecimal` has no negative zero while `Decimal` does, so results are normalised (`-0.00` never appears)
- `allocate/2` is an E-CoreBank utility that Fineract does not have; it is documented as such and covered by property tests rather than by the golden master

## 8. Build order

1. Currency and `Money` with scale, comparison and addition and subtraction (done)

## 9. Contract tests

No Fineract integration-test class targets this library directly. It is checked by property-based tests and by the differential runner comparing calculation results with Fineract.

## 10. Acceptance criteria

Module-specific:

- No function accepts or returns a float (floats raise `ArgumentError`)
- Property tests: addition is commutative and associative, plus-then-minus is the identity, rounding is idempotent, allocation always sums to the original
- Golden-master results match Fineract's `Money` for the generated corpus across every rounding mode (done: 130,144 of 130,144)
- Interest primitives (simple and compound factors, period fractions) match Fineract for a generated corpus (not started)

Common to every module:

- Contract probe: every `must` read operation of this module passes against the oracle (status and response shape).
- Fineract's integration-test classes listed above pass, or each failure is recorded as a divergence with an ADR.
- Every state-changing operation goes through the command bus: validated, authorised, audited, idempotent, maker-checker aware.
- Every table has an Ecto migration in the tenant repo that matches the Fineract schema, and the cross-tenant isolation test covers the module.
- Money uses `Decimal` with an explicit currency and rounding rule; no floats.
- Dependencies point only at the modules in the header. `mix xref` finds no cycle or reverse dependency.
- `mix format`, Credo strict, Dialyzer and the module's tests pass; the module README and this document are updated.
