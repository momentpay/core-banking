## 1. Purpose

Everything that runs on a schedule or at end of day: the job scheduler and its history, the close-of-business process built from ordered business steps with partitioned processing across worker nodes, the loan account locks that keep real-time writes consistent while COB runs, catch-up after missed days, and inline COB for a single account. Fineract implements this on Spring Batch; we use Oban.

## 2. Responsibilities

- Scheduled jobs and their parameters and run history (`job`, `job_parameters`, `job_run_history`, `scheduler_detail`)
- COB for loans, savings and working-capital loans as ordered business steps (`m_batch_business_steps`: `job_name`, `step_name`, `step_order`)
- Partitioned processing with a manager and workers; retry and resume; state kept per execution
- Loan account locks (`m_loan_account_locks`: `loan_id`, `lock_owner`, `error`, `lock_placed_on_cob_business_date`, `stacktrace`), soft and hard, with bypass for repair and the orphaned-lock cleanup step
- Inline COB for one loan when a real-time write meets a soft lock
- COB catch-up after a missed or replayed day; business-date roll after COB
- The interest-posting, accrual and similar jobs the product modules define as steps

## 3. Out of scope

- What a business step does (it lives in the product module that owns it)
- The business-date model itself (ecb_platform)

## 7. Design to follow

- Soft lock: COB is queued for a loan but no worker has it, so a real-time write runs an inline COB for that loan first. Hard lock: a worker holds the loan, so writes are rejected with HTTP 409. `bypass_enabled` allows repair calls on a locked loan
- A lock with an error stays in place deliberately: it marks a loan that must be fixed; only locks without an error whose COB date has completed are removed by the cleanup step
- COB date is derived from the business date by a strategy; transactions arriving during COB belong to the next business day
- Steps are configuration, not code paths: the order is read from the business-step table so an operator can change it
- Partitioned processing: a manager splits accounts into chunks and workers process them; failure of one chunk must not block others, and the run is resumable
- Instance roles: only batch nodes run jobs; write and read nodes do not

## 8. Build order

1. Scheduler and job history on Oban
2. Business-date roll and the COB date strategy
3. Lock table and soft and hard lock behaviour
4. Loan COB with the standard business steps, partitioned
5. Inline COB and catch-up
6. Savings COB, then working-capital COB
7. Operations views: job status, locked loans

## 10. Acceptance criteria

Module-specific:

- Killing a worker mid-run and restarting completes the run without double processing
- A real-time repayment during COB behaves as Fineract does for both soft and hard locks
- Replaying a missed day produces the same results as running it on time
- The COB, scheduler and catch-up integration classes pass

Common to every module:

- Contract probe: every `must` read operation of this module passes against the oracle (status and response shape).
- Fineract's integration-test classes listed above pass, or each failure is recorded as a divergence with an ADR.
- Every state-changing operation goes through the command bus: validated, authorised, audited, idempotent, maker-checker aware.
- Every table has an Ecto migration in the tenant repo that matches the Fineract schema, and the cross-tenant isolation test covers the module.
- Money uses `Decimal` with an explicit currency and rounding rule; no floats.
- Dependencies point only at the modules in the header. `mix xref` finds no cycle or reverse dependency.
- `mix format`, Credo strict, Dialyzer and the module's tests pass; the module README and this document are updated.
