## 1. Purpose

How the core tells the outside world what happened. Business events are written to an outbox table in the same transaction as the change and published in order, at least once, in a standard format. Hooks and webhooks call external URLs, notifications reach users, and external services (SMS gateway, email, content storage) are configured here. It is the second integration surface after the API.

## 2. Responsibilities

- Transactional outbox for business events (`m_external_event`: `type`, `schema`, `data`, `status`, `business_date`, `aggregate_root_id`, `category`, `idempotency_key`, `sent_at`)
- Event publication with ordering and at-least-once delivery, selective producing per event type, bulk events
- Event configuration (which event types are produced)
- Hooks and webhooks (`m_hook` family) for events
- In-app notifications (`m_notification`, `notification_generator`, `notification_mapper`)
- External service configuration (`c_external_service`)

## 3. Out of scope

- SMS and email campaigns, interoperation: deferred
- Consumers of the events: external systems

## 7. Design to follow

- The event is stored in the same database transaction as the business change, so an event exists if and only if the change committed
- Fineract serialises events as Avro, with the schema name stored beside the payload (`schema` column), and defines a standard event envelope; we follow its event types and field names so consumers written for Fineract keep working
- Delivery is at least once and ordered per aggregate; consumers must be idempotent, and the `idempotency_key` column supports that
- Publication runs on batch-role nodes, not on request-handling nodes

## 8. Build order

1. Outbox table and the write path in the command pipeline
2. Publisher with ordering, retry and status tracking
3. Event configuration API
4. Hooks and webhooks
5. Notifications

## 10. Acceptance criteria

Module-specific:

- A command that rolls back leaves no event
- Killing the publisher mid-batch and restarting delivers every event at least once, in order
- Event payloads for a generated scenario match Fineract's field for field

Common to every module:

- Contract probe: every `must` read operation of this module passes against the oracle (status and response shape).
- Fineract's integration-test classes listed above pass, or each failure is recorded as a divergence with an ADR.
- Every state-changing operation goes through the command bus: validated, authorised, audited, idempotent, maker-checker aware.
- Every table has an Ecto migration in the tenant repo that matches the Fineract schema, and the cross-tenant isolation test covers the module.
- Money uses `Decimal` with an explicit currency and rounding rule; no floats.
- Dependencies point only at the modules in the header. `mix xref` finds no cycle or reverse dependency.
- `mix format`, Credo strict, Dialyzer and the module's tests pass; the module README and this document are updated.
