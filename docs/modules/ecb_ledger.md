## 1. Purpose

Fineract-style accounting: the chart of GL accounts, the accounting rule that each product carries (none, cash, periodic accrual or upfront accrual), the mappings from financial activities and payment types to accounts, and the journal entries that every deposit and loan event produces. It also owns closures, manual journal entries, accrual runs and loan provisioning. This follows Fineract exactly (decision of 14 Nov 2026), with an export port reserved for a later Finacle integration.

## 2. Responsibilities

- GL accounts and hierarchy (`acc_gl_account`), with account types, usage (header or detail) and tags
- Product accounting rules and `acc_product_mapping`: which GL account each kind of movement hits for a product
- Financial activity and payment-type account mappings (`acc_gl_financial_activity_account`)
- Journal entries (`acc_gl_journal_entry`) with reversal, running balances per office and organisation, and links to the originating loan, savings or client transaction
- Manual journal entries, opening balances, journal-entry aggregation summaries
- Closures (`acc_gl_closure`) that prevent posting before a date
- Periodic accrual accounting run, provisioning criteria, categories, history and entries
- A `GlExport` port with extraction state, empty until a Finacle adapter is scoped

## 3. Out of scope

- Deciding when a loan or savings event happens: the product modules raise events and call this module
- The Finacle adapter itself (later)
- Reports over the ledger (ecb_reports), except the trial balance tables owned here

## 7. Design to follow

- A journal is posted in the same transaction as the business change, and only when the product's accounting rule is not none
- Double entry is enforced by a deferred database constraint so an unbalanced journal cannot commit
- `acc_gl_journal_entry` carries `loan_transaction_id`, `savings_transaction_id`, `client_transaction_id` and `share_transaction_id`, so a journal can always be traced to its cause; keep those columns
- Reversal is a new journal with `reversal_id` pointing back, never an update of the original
- Running balances are calculated per office and per organisation (`is_running_balance_calculated`, `office_running_balance`, `organization_running_balance`)
- Accounting events are mapped by product type and financial activity; keep the mapping data-driven as Fineract does

## 8. Build order

1. GL accounts, tags and the account API (done)
2. Financial-activity and payment-type mappings
3. Journal entry posting service with the balance constraint, then reversal
4. Product account mapping and the accounting rules (cash first, then accrual)
5. Closures and manual entries
6. Provisioning criteria, categories and entries
7. Aggregation summaries and the trial balance
8. The `GlExport` port

## 10. Acceptance criteria

Module-specific:

- An unbalanced journal cannot be committed, tested at the database
- Posting before the closure date is rejected
- Journals for savings and loan scenarios match Fineract's on a generated corpus, line by line
- The Fineract accounting and provisioning integration classes pass

Common to every module:

- Contract probe: every `must` read operation of this module passes against the oracle (status and response shape).
- Fineract's integration-test classes listed above pass, or each failure is recorded as a divergence with an ADR.
- Every state-changing operation goes through the command bus: validated, authorised, audited, idempotent, maker-checker aware.
- Every table has an Ecto migration in the tenant repo that matches the Fineract schema, and the cross-tenant isolation test covers the module.
- Money uses `Decimal` with an explicit currency and rounding rule; no floats.
- Dependencies point only at the modules in the header. `mix xref` finds no cycle or reverse dependency.
- `mix format`, Credo strict, Dialyzer and the module's tests pass; the module README and this document are updated.
