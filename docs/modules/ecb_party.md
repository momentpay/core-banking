## 1. Purpose

The customer master. Individual and entity clients, their identifiers, addresses, family members, charges and transactions, the client lifecycle (pending, active, closed, rejected, withdrawn, reactivated), transfers between offices, and client search. Clients are what accounts hang off, so this module comes right after the reference data.

## 2. Responsibilities

- Client lifecycle and status transitions through commands (`?command=activate`, `close`, `reject`, `withdraw`, `reactivate`, `undoreject`, `undowithdrawal`, `assignStaff`, `unassignStaff`, `updateSavingsAccount`, `proposeTransfer` and related)
- Individual and non-person (entity) clients (`m_client`, `m_client_non_person`)
- Identifiers (`m_client_identifier`), addresses (`m_address`, `m_client_address`), family members (`m_family_members`)
- Client charges and client transactions (`m_client_charge`, `m_client_transaction`)
- Client attendance and transfer details between offices
- Search (the v1 search and the v2 `ClientSearchV2`)

## 3. Out of scope

- Groups and centres: deferred
- Client collateral (ecb_collateral)
- KYC workflow and onboarding journeys: the core stays core; those live in surrounding systems

## 7. Design to follow

- 20 tables reference `m_client`; the client id is a stable key for the whole system
- Client state is a status enum with a controlled set of transitions, each a command with its own permission
- Entity clients use `m_client_non_person` with the legal-form code values; a bank pilot needs this from the start
- External ids are supported everywhere; many Fineract endpoints address a client by `external-id/{externalId}`
- Client search v2 is paged and filterable; follow Fineract's contract exactly because the Mifos console depends on its shape

## 8. Build order

1. Client create, read, update with the command pipeline
2. Lifecycle commands (activate, close, reject, withdraw, reactivate)
3. Identifiers, addresses, family members
4. Client charges and transactions (needs ecb_catalog and ecb_ledger)
5. Transfer between offices; search v1 and v2

## 10. Acceptance criteria

Module-specific:

- Every status transition and every rejected transition matches Fineract's responses
- Client create and update responses (including `changes`) match the oracle's shape
- The client integration classes (client, identifier, family member, charges, transaction, search, external id) pass

Common to every module:

- Contract probe: every `must` read operation of this module passes against the oracle (status and response shape).
- Fineract's integration-test classes listed above pass, or each failure is recorded as a divergence with an ADR.
- Every state-changing operation goes through the command bus: validated, authorised, audited, idempotent, maker-checker aware.
- Every table has an Ecto migration in the tenant repo that matches the Fineract schema, and the cross-tenant isolation test covers the module.
- Money uses `Decimal` with an explicit currency and rounding rule; no floats.
- Dependencies point only at the modules in the header. `mix xref` finds no cycle or reverse dependency.
- `mix format`, Credo strict, Dialyzer and the module's tests pass; the module README and this document are updated.
