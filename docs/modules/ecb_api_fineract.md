## 1. Purpose

The wire contract: the paths, JSON shapes, `?command=` actions, templates, pagination, error format, tenant header and authentication that existing Fineract clients and the Mifos web and mobile apps expect. It is a thin layer over the domain modules and owns no business rules. It starts in Phase 1 with authentication and `GET /offices` and grows module by module, always measured by the contract probe.

## 2. Responsibilities

- Routing under `/fineract-provider/api/v1/...` and `/v2/...` for every `must` and `should` operation in the inventory
- Request parsing and response serialisation with Fineract's field names, date formats (arrays such as `[2009,1,1]`) and enumeration objects
- The `?command=<action>` convention for state transitions and the `template` endpoints
- Pagination, filtering and sorting parameters, including `pageItems` and `totalFilteredRecords`
- Error responses in Fineract's format (`developerMessage`, `httpStatusCode`, `defaultUserMessage`, `errors` list)
- Tenant header, authentication and idempotency header handling at the edge
- A documented 'not implemented' error for every deferred operation

## 3. Out of scope

- Business rules: they live in the domain modules
- Our own API design (ecb_api_native)

## 6. Data model

This module owns no tables.

## 7. Design to follow

- A thin controller per resource that builds a command or a query and delegates; no logic in controllers
- Serialisation modules per resource mirror Fineract's `serialization` packages, because the field names and shapes are the contract
- The OpenAPI descriptor in `parity/inventory` is the reference; a CI job compares our generated descriptor with it for the implemented operations
- Compatibility is tested, not assumed: the contract probe compares status and shape against the oracle, Fineract's own tests compare behaviour

## 8. Build order

1. Tenant header, authentication, error format, `GET /offices` (done)
2. Read endpoints of the reference data and administration resources (done)
3. Write endpoints of the organisation and administration resources, through the command pipeline (done)
4. Maker-checker inbox, then clients and catalog resources (next)
5. Deposits resources, then loans resources
6. Accounting, reports, hooks and the remaining `must` operations
7. The `should` operations; the deferred operations return 'not implemented'

## 9. Contract tests

Verified by the contract probe over all read operations and by Fineract's whole integration suite, which drives the API.

## 10. Acceptance criteria

Module-specific:

- Contract probe pass rate rises monotonically and reaches 100% of counted `must` read operations (now 20 of 146)
- Fineract's integration suite pass rate per module meets that module's acceptance criteria
- The stock Mifos web app logs in and browses every implemented area

Common to every module:

- Contract probe: every `must` read operation of this module passes against the oracle (status and response shape).
- Fineract's integration-test classes listed above pass, or each failure is recorded as a divergence with an ADR.
- Every state-changing operation goes through the command bus: validated, authorised, audited, idempotent, maker-checker aware.
- Every table has an Ecto migration in the tenant repo that matches the Fineract schema, and the cross-tenant isolation test covers the module.
- Money uses `Decimal` with an explicit currency and rounding rule; no floats.
- Dependencies point only at the modules in the header. `mix xref` finds no cycle or reverse dependency.
- `mix format`, Credo strict, Dialyzer and the module's tests pass; the module README and this document are updated.
