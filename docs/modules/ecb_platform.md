## 1. Purpose

The foundation every other module stands on. It resolves the tenant for each request or job and gives it a database, authenticates and authorises users, and runs every state-changing operation through one command pipeline that validates, checks permission and maker-checker, executes in a transaction, records the command, and guarantees idempotency. It also owns the business date, global configuration, data tables, the Batch API and the user, role and permission model. Fineract calls this slice `fineract-core`, `fineract-security`, `fineract-command*` and the `infrastructure` and `useradministration` packages of the provider.

## 2. Responsibilities

- Tenancy: registry, dynamic repo per tenant, per-tenant migrations, tenant resolved from the `Fineract-Platform-TenantId` header or job metadata (built)
- Authentication: HTTP basic with the `/authentication` call that returns a base64 key, OAuth2 resource server, OIDC federation, two-factor
- Authorisation: users, roles and permissions (`m_appuser`, `m_role`, `m_permission` with a `can_maker_checker` flag per permission); a permission check on every API
- Command pipeline: command wrapper, handler registry, before/after/error hooks, command store and audit (`m_portfolio_command_source`, `m_command`)
- Maker-checker: run the command, validate for real, roll back, log `Pending`; approve re-runs it under the checker
- Idempotency: unique (key, action, entity); replay returns the stored result; in-flight returns HTTP 409
- Business date and COB date (`m_business_date` with a `type` column), exposed through the business-date API
- Global configuration (`c_configuration`, including trap-door flags), instance mode (read, write, batch roles per node)
- Data tables engine: tenant-defined extension tables and entity data-table checks (`x_registered_table`, `m_entity_datatable_check`)
- Batch API (several operations in one request), ad-hoc query, bulk import, templates

## 3. Out of scope

- Scheduled jobs and close of business (ecb_batch)
- Hooks, webhooks and the event outbox (ecb_events)
- Domain rules of any product: this module knows nothing about clients, loans or deposits

## 7. Design to follow

- Command/query separation: writes are commands persisted in `m_portfolio_command_source` (columns include `action_name`, `entity_name`, `command_as_json`, `maker_id`, `checker_id`, `status`, `idempotency_key`, `result`, `result_status_code`, `client_ip`); reads are plain queries. Fineract's newer framework (`fineract-command`) adds a dispatcher, typed handlers and an `m_command` table with a `state` and approval timestamps; we follow the newer shape and keep the older table for parity
- Fineract's own docs call its legacy command path 'a little bit convoluted'. Keep the behaviour (statuses, audit, maker-checker semantics) but implement it as one small pipeline: `Command` struct, `Handler` behaviour, ordered steps, an `Ecto.Multi`
- Idempotency uses the header `Idempotency-Key` (the configuration default). A completed replay sets `x-served-from-cache: true`. Batch items can carry their own key
- Permissions are fine-grained and per API; `can_maker_checker` marks which actions can be put under four-eyes. Roles bundle permissions
- Tenant database password is never stored in the registry (a deliberate divergence from Fineract, which stores it encrypted with a master password). The registry holds the name of an environment variable
- Instance roles (read, write, batch) are runtime configuration of one release, as in Fineract's `fineract.mode.*` flags; the read role may use a replica
- The API is stateless; no session state on the server
- Business date is a logical date separate from the calendar. Components never call the system clock for business logic; they ask the `Clock` behaviour

## 8. Build order

1. Command struct, handler registry, pipeline and command store with audit columns (done)
2. Idempotency table and the replay and 409 rules (done, inside the pipeline: the unique key on `m_portfolio_command_source`)
3. Permissions, roles and users in the tenant schema with Fineract's seed data (done); the `/authentication` endpoint with basic auth (next)
4. Maker-checker: the pending, approve, reject and delete flow (done in `Commands`); the `/makercheckers` API (next, with the API layer)
5. Business date and `Clock`, with the business-date API (next)
6. Global configuration admin and instance mode
7. Batch API
8. Data tables engine (entities are registered by name, so no dependency on ecb_org), bulk import, ad-hoc query, templates
9. OAuth2 and OIDC, two-factor

## 10. Acceptance criteria

Module-specific:

- A write sent twice with the same `Idempotency-Key` executes once; the second response is served from the stored result (done: tested, including eight concurrent identical requests)
- A maker-checker command leaves a `Pending` entry and no data change; approval applies it exactly once (done: tested)
- Cross-tenant isolation test: a command run for tenant A is invisible in tenant B's database (to do: needs a second tenant database)
- The Fineract classes for authentication, roles, users, password preferences, maker-checker, global configuration, idempotency and the Batch API pass (to do: needs the API layer)

Common to every module:

- Contract probe: every `must` read operation of this module passes against the oracle (status and response shape).
- Fineract's integration-test classes listed above pass, or each failure is recorded as a divergence with an ADR.
- Every state-changing operation goes through the command bus: validated, authorised, audited, idempotent, maker-checker aware.
- Every table has an Ecto migration in the tenant repo that matches the Fineract schema, and the cross-tenant isolation test covers the module.
- Money uses `Decimal` with an explicit currency and rounding rule; no floats.
- Dependencies point only at the modules in the header. `mix xref` finds no cycle or reverse dependency.
- `mix format`, Credo strict, Dialyzer and the module's tests pass; the module README and this document are updated.
