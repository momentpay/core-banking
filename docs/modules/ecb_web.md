# ecb_web: LiveView console (the Mifos rewrite)

> **Phase** 2  |  **Status** Phoenix shell exists; no console screens  |  **Depends on** `ecb_platform`, `ecb_api_fineract`

Generated parts of this document (the Fineract reference, API scope, data model and tests) come from
`parity/` inventories and are regenerated by `python parity/tools/module_docs.py build`. The rest is the
design and lives in `docs/modules/modules.json`. Overall approach: [design reference](../design/00-fineract-design-reference.md), [ADR-0001](../adr/0001-follow-fineract-design.md).

## 1. Purpose

The operations console, replacing the Mifos web app. It is built as screens over the domain contexts in LiveView, one area at a time, starting with the screens staff use daily. Until a screen exists the stock Mifos web app can run against the compatible API, so there is always a usable console while this one is built.

## 2. Responsibilities

- A design system: tables, forms, wizards, detail tabs, search, the maker-checker inbox
- Screens per area, in the order of the module build: organisation, clients, deposits, loans, accounting, administration
- Login, tenant selection, permission-aware navigation
- Dashboards and operational views (job status, locked loans, pending approvals)

## 3. Out of scope

- The mobile apps and customer self-service: API clients, kept as they are
- Business rules: the console calls the same command and query layers as the API

## 6. Data model

This module owns no tables.

## 7. Design to follow

- Fineract is headless and has no console of its own; the Mifos web app is the reference for what screens and flows staff need
- Screens never bypass the command pipeline, so audit and maker-checker behave the same as through the API
- The grid component is AG Grid Enterprise, already vendored in `assets/vendor` under the licence the team holds; record the licence terms in an ADR

## 8. Build order

1. Design system and the shell with login
2. Organisation and reference-data screens
3. Client screens, then deposit screens, then loan screens
4. Accounting and administration screens, the maker-checker inbox
5. Retire the Mifos web app per area once the screens reach parity

## 9. Contract tests

No Fineract test class applies. Screens are checked against the Mifos web app's flows with recorded browser tests.

## 10. Acceptance criteria

Module-specific:

- For each area, recorded flows from the Mifos web app pass against the LiveView screens
- Permission checks hide and deny exactly what the API denies

Common to every module:

- Contract probe: every `must` read operation of this module passes against the oracle (status and response shape).
- Fineract's integration-test classes listed above pass, or each failure is recorded as a divergence with an ADR.
- Every state-changing operation goes through the command bus: validated, authorised, audited, idempotent, maker-checker aware.
- Every table has an Ecto migration in the tenant repo that matches the Fineract schema, and the cross-tenant isolation test covers the module.
- Money uses `Decimal` with an explicit currency and rounding rule; no floats.
- Dependencies point only at the modules in the header. `mix xref` finds no cycle or reverse dependency.
- `mix format`, Credo strict, Dialyzer and the module's tests pass; the module README and this document are updated.
