# ecb_org: Organisation and reference data

> **Phase** 2  |  **Status** in progress (14 Nov 2026). Built, and checked against responses recorded from Fineract: the read side of offices, currencies, codes and code values, payment types, working days, funds, holidays, staff and account-number formats; and the write side of offices (create, update, with the hierarchy), funds, payment types, staff, codes and code values, working days and holidays (create, update, activate, delete). Still to do: the organisation currency selection, the office money transfer, documents, notes, images, bulk import and global search.  |  **Depends on** `ecb_money`, `ecb_platform`

Generated parts of this document (the Fineract reference, API scope, data model and tests) come from

design and lives in `docs/modules/modules.json`. Overall approach: [design reference](../design/00-fineract-design-reference.md), [ADR-0001](../adr/0001-follow-fineract-design.md).

## 1. Purpose

The reference data every other module reads: offices and their hierarchy, staff, currencies enabled for the tenant, codes and code values, holidays, working days, payment types, funds, notes, documents and images, account-number formats, the global search. It is read-heavy and changes rarely, so it is the natural second module and the first slice that makes the Mifos console usable.

## 2. Responsibilities

- Offices and the office hierarchy (`m_office`), office transactions
- Staff (`m_staff`) and assignment of loan officers
- Currencies and the tenant's selected currencies (`m_currency`, `m_organisation_currency`), feeding ecb_money
- Codes and code values (`m_code`, `m_code_value`), including the system codes other modules rely on
- Holidays (`m_holiday`, `m_holiday_office`) and working days (`m_working_days`), with the rescheduling rules that loans use
- Payment types and payment details (`m_payment_type`, `m_payment_detail`), funds (`m_fund`)
- Notes, documents, images and the content store (local file system first; S3 later)
- Account number format preferences
- Global search and the cross-entity template and mapping tables

## 3. Out of scope

- Clients (ecb_party)
- Calendars and meetings: group-based, deferred
- Data tables engine (ecb_platform)
- Tellers and cashiers (ecb_branch), which post journals and so depend on ecb_ledger

## 7. Design to follow

- 17 tables reference `m_office`; offices are the unit of scoping for users, clients and accounts, so the office hierarchy and the user-to-office visibility rule are implemented once here and reused everywhere
- Holidays carry a rescheduling type and apply to offices; the effect on repayment dates is computed in ecb_loans from data served here
- Code values are stable identifiers other tables store as ids; keep ids and names exactly, because clients and loans reference them
- Document storage sits behind a behaviour with a file-system adapter and an S3 adapter, as in Fineract's content store

## 8. Build order

1. Read and write of offices, funds, payment types, staff, codes and code values, working days, holidays (done)
2. Currencies: the organisation's selected currencies (next)
3. Notes, documents, images and the content store
4. Office money transfers and bulk import
5. Global search

## 10. Acceptance criteria

Module-specific:

- Office hierarchy queries and the user visibility rule match Fineract on a generated tree
- Holiday and working-day rescheduling results match Fineract for a corpus of dates
- Every `must` read operation of this module passes the contract probe

Common to every module:

- Contract probe: every `must` read operation of this module passes against the oracle (status and response shape).
- Fineract's integration-test classes listed above pass, or each failure is recorded as a divergence with an ADR.
- Every state-changing operation goes through the command bus: validated, authorised, audited, idempotent, maker-checker aware.
- Every table has an Ecto migration in the tenant repo that matches the Fineract schema, and the cross-tenant isolation test covers the module.
- Money uses `Decimal` with an explicit currency and rounding rule; no floats.
- Dependencies point only at the modules in the header. `mix xref` finds no cycle or reverse dependency.
- `mix format`, Credo strict, Dialyzer and the module's tests pass; the module README and this document are updated.
