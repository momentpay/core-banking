## 1. Purpose

The report engine: stored SQL reports with parameters that operators can run and export, the standard report library Fineract ships, and report mailing jobs that run reports on a schedule and send the result. Fineract's reports are SQL stored in the database and reference its tables, which is a main reason the schema is kept compatible.

## 2. Responsibilities

- Report definitions and parameters (`stretchy_report`, `stretchy_report_parameter`, `stretchy_parameter`)
- Running reports with permission checks, output formats and the available-exports list
- The standard report library, loaded into each tenant
- Report mailing jobs and their run history
- Protection against SQL injection in report parameters

## 3. Out of scope

- Statutory and regulatory returns for the pilot country: a separate piece of work
- Business intelligence and warehousing: consume the event stream instead

## 7. Design to follow

- Reports are data: SQL text plus parameters, executed read-only. Because they name Fineract tables and columns directly, keeping the schema compatible lets the whole standard library run unchanged
- Parameters are bound, never interpolated; Fineract has a dedicated SQL-injection test and we keep it
- Report execution uses a read-only connection and, when configured, a read replica

## 10. Acceptance criteria

Module-specific:

- The standard reports return the same rows as Fineract on the same data
- The SQL-injection test passes: hostile parameters never alter the statement

Common to every module:

- Contract probe: every `must` read operation of this module passes against the oracle (status and response shape).
- Fineract's integration-test classes listed above pass, or each failure is recorded as a divergence with an ADR.
- Every state-changing operation goes through the command bus: validated, authorised, audited, idempotent, maker-checker aware.
- Every table has an Ecto migration in the tenant repo that matches the Fineract schema, and the cross-tenant isolation test covers the module.
- Money uses `Decimal` with an explicit currency and rounding rule; no floats.
- Dependencies point only at the modules in the header. `mix xref` finds no cycle or reverse dependency.
- `mix format`, Credo strict, Dialyzer and the module's tests pass; the module README and this document are updated.
